## 1. Постановка задачи

Входной поток обращений распределяется между операторами и партнерами. Для каждого обращения требуется оценить вероятность успешного целевого действия в течение 5 дней после назначения. Итоговый score используется для ранжирования обращений внутри дня: более перспективные обращения должны получать более высокий score.

Одна строка `train.csv`/`test.csv` соответствует факту назначения обращения в конкретный момент времени и содержит контекст назначения (источник, регион, канал), признаки пользователя, продавца и объявления, а также агрегаты активности за окна `1d`–`90d`. `events.csv` предоставляет более гранулярную историю событий для дополнительного feature engineering.

**Метрика — Daily Average Precision.** AP вычисляется отдельно для каждой даты назначения, итоговое значение — среднее по дням:

$$AP = \frac{1}{N_+}\sum_{k=1}^NPrecision@k ** y_{(k)}$$

$$Precision@k = \frac{\sum_{j=1}^k y_{(i)}}{k}$$​​$$N_+ = \sum_{i=1}^Ny_i$$

$$AP_{d} = AP({(y_i, s_i): assignment date_i = d})$$

$$DailyAP = \frac{1}{|D|}\sum_{d \in D}AP_d$$


**Ограничения задачи:** запрещено использование LLM с числом параметров свыше 1B и обращение к внешним API; запрещена ручная разметка тестовых данных; запрещен хардкод под конкретные `lead_id`. Использование open-source библиотек допускается при условии их раскрытия в описании решения.

## 4. Разведочный анализ данных

Перед построением признаков были проверены четыре гипотезы:

- **Стабильность target rate по дням.** Значение колеблется в диапазоне 0.19–0.25 без выраженного тренда, что позволяет применять валидацию по времени без риска систематического смещения оценки.
- **Информативность категориальных признаков.** `lead_source` и `call_center` демонстрируют существенную разницу в target rate между уровнями; `region`, `user_tenure_bucket`, `price_bucket` показывают слабую дискриминирующую способность.
- **Пересечение train/test.** Множества `user_id` не пересекаются, тестовая выборка целиком расположена после обучающей по времени назначения. Это делает валидацию по времени обязательным требованием, а не вопросом выбора.
- **Природа пропущенных значений.** Гипотеза о связи пропусков с "новизной" пользователя проверена тремя независимыми методами: критерий Манна-Уитни по `user_age_days` (p-value > 0.05), корреляция масок пропусков между признаками (близка к нулю вне диагонали — пропуски в разных колонках возникают независимо друг от друга), пересечение множества строк с пропусками и множества лидов без событий в `events.csv` (пересечение минимально). Все три проверки указывают на случайный характер пропусков (MCAR). Исходя из этого, дополнительные индикаторные признаки (`is_new_user` и подобные) не вводились — пропуски передаются моделям в исходном виде, поскольку CatBoost, LightGBM и XGBoost поддерживают NaN нативно.

## 5. Feature engineering

Готовые табличные признаки (окна `1d`–`90d`, история назначений, контекст) покрывают базовый уровень сигнала. Основной прирост качества получен за счет признаков, построенных из сырой последовательности событий в `events.csv`.

Обязательное условие для всех признаков этого раздела: `event_ts < assignment_ts`, применяемое строго до агрегации. Датасет `events.csv` намеренно содержит события, произошедшие после момента назначения, — использование таких событий приводит к утечке целевой переменной.

### 5.1. Оконные агрегаты и recency

Счетчики событий по типам построены для окон `12h/1d/3d/7d/14d/30d` — окно `12h` добавлено дополнительно к готовым суточным агрегатам, поскольку для ранжирования внутри дня разница между активностью "два часа назад" и "вчера утром" может быть существенной. Recency-признаки (`ev_{type}_r`, минимальное время до события каждого типа) дополнены бинарными индикаторами наличия событий в каждом окне (`ev_has_{window}`) — отдельно от значения счетчика, поскольку "ноль событий" и "отсутствие данных" представляют разную информацию для древовидной модели.

### 5.2. Экспоненциально взвешенная активность

Жесткие оконные границы вносят разрыв на границе окна: событие час назад и событие за час до истечения недельного окна попадают в одну категорию. В качестве альтернативы построена экспоненциально затухающая сумма активности с двумя значениями half-life (24 и 168 часов):

$$
decay\_sum = \sum \exp\left( - \ln(2) \cdot \frac{hours\_before_i}{half\_life} \right)
$$

Признак не имеет разрывов на границах окна и точнее отражает распределение активности во времени.

### 5.3. Контекст последнего события

Наиболее значимый отдельный признак, полученный в ходе разработки, — контекст **непосредственно последнего** события перед назначением (`last_ctx_seq`, `last_src_slot`, `last_event_type`), а не производные статистики по всей истории (число уникальных значений, мода). В разведочном анализе разные значения `ctx_seq` демонстрировали существенно различный target rate, однако этот сигнал ранее не передавался модели в явном виде. Добавление `last_ctx_seq`/`last_src_slot` дало прирост **+0.02 Daily AP** на кросс-валидации, устойчивый на всех четырех фолдах.

Дополнительно построено распределение долей `ctx_seq` (`ctx_share_*`, 8 уникальных значений) — более детализированная версия того же сигнала по сравнению с модой и числом уникальных значений, которые сохранены как более устойчивая оценка при малом числе событий у лида.

### 5.4. Динамика и структура активности

- `ev_avg_interval` — средний интервал между последовательными событиями, характеризует плотность активности.
- `n_sessions` — число визитов, где визитом считается серия событий без пауз более 6 часов между ними; отличает единичный интенсивный визит от многократных коротких обращений при одинаковом суммарном числе событий.
- `decay_momentum_ratio` — отношение суточной экспоненциальной суммы к недельной, индикатор роста или затухания интереса непосредственно перед назначением.

### 5.5. Ценовые статистики по истории просмотров

`ev_price_mean/std/min/max` — статистики `item_price_log` по всем просмотренным лидом объявлениям. Высокое значение `ev_price_std` указывает на широкий диапазон рассматриваемых предложений, а не фокус на одном объявлении.

### 5.6. Долевые признаки по типам событий

`ratio_{event_type}_to_total` — доля каждого типа события в общей активности лида. Абсолютные счетчики не различают пользователя, который только просматривает объявления, и пользователя с сопоставимым числом просмотров, но систематически переходящего к контакту с продавцом; долевые признаки делают это различие явным.

### 5.7. Производные признаки на основе табличных агрегатов

- **Конверсия истории назначений** — `prior_success_ratio_30d`, `prior_answer_ratio_30d`: доля успешных/отвеченных обращений от общего числа назначений за 30 дней, а не абсолютное количество.
- **Активность и вовлеченность пользователя** — `user_active_ratio`, `user_activity_per_lead`, `user_engagement_score`, `user_total_views_30d`, `user_total_actions_30d`.
- **Экономические показатели объявления** — `price_per_year`, `mileage_per_year`, `price_per_mileage`, `car_age_log`: цена и пробег в отношении к возрасту автомобиля, а не в абсолютном выражении.
- **Позиция цены относительно рынка** — `price_pct_in_segment`, `price_pct_in_region`: процентиль цены объявления в рамках своего `car_segment`/`region`.
- **Показатели продавца** — `seller_quality` (произведение response rate и размера инвентаря), `seller_activity` (просмотры продавца относительно размера инвентаря).
- **Динамика между окнами** — `views_trend_1d_to_7d`, `views_trend_7d_to_30d`, `search_trend_7d_to_30d`, `contacts_trend_7d_to_30d`: отношение короткого окна к длинному, индикатор недавнего роста активности относительно исторического уровня.
- **Воронка вовлечения** — `favorites_per_view_30d`, `detail_expands_per_view_30d`, `photo_swipes_per_view_30d`, `contacts_per_view_30d`, `chat_per_contact_30d`, `call_per_contact_30d`, `chat_call_ratio_30d`, `search_to_views_ratio`, `refinements_per_search` — доли перехода между последовательными этапами взаимодействия.
- **Признаки взаимодействия** — `age_price_interaction`, `inventory_price_interaction`, `activity_seller_interaction` — произведения признаков в случаях, когда эффект одного, предположительно, зависит от уровня другого.

### 5.8. Отбор признаков

Итоговый набор из 229 признаков избыточен относительно объема выборки (13.7k строк). Отбор выполнен по важности признаков одной предварительной модели CatBoost (`get_feature_importance()`), порог отсечения подобран перебором по кросс-валидации:

| Признаков всего | Порог важности | Осталось | CV Daily AP |
|---:|:---:|---:|---:|
| 229 | — | 229 | 0.6607 |
| 229 | ≥ 0.05 | **188** | **0.6650** |
| 229 | ≥ 0.10 | ~200 | 0.6623 |

Порог 0.05 показал наилучший результат: более низкий порог сохраняет шумовые признаки, более высокий отсекает признаки со слабым индивидуальным вкладом, но полезные во взаимодействии с другими.

## 6. Валидация

### 6.1. Соответствие метрике задачи

Daily Average Precision оценивает качество ранжирования отдельно внутри каждой даты назначения, а не по выборке в целом. Валидационная метрика должна воспроизводить эту структуру: усредненный по всей выборке AP отвечает на другой вопрос и может маскировать проблемы ранжирования в отдельные дни. Функция `daily_average_precision` реализована в точном соответствии с формулой из условия задачи — группировка по `assignment_date`, `average_precision_score` внутри группы, среднее по группам.

### 6.2. Схема разбиения

Случайное разбиение (`train_test_split`) неприменимо по двум причинам: множества `user_id` в train и test не пересекаются, и тестовая выборка целиком расположена после обучающей по датам назначения — это установлено в разделе EDA, а не предполагается. Применена схема `TimeSeriesSplit` по уникальным датам назначения: 4 фолда с расширяющимся окном, где обучающая выборка растет, а валидационная — очередной, еще не использованный блок дат. Схема напрямую воспроизводит условия, в которых решение будет работать на скрытой тестовой выборке.

Количество фолдов (4) определено ограничением данных: в обучающей выборке 16 уникальных дат. Увеличение числа фолдов сокращает размер валидационного блока до 1–2 дат, при котором оценка Average Precision одного дня начинает определять результат всего фолда, что делает оценку избыточно шумной.

### 6.3. Оценка устойчивости результата

Наряду со средним значением Daily AP (0.686) фиксируется стандартное отклонение по фолдам (± 0.033). Данная величина использована для интерпретации итогового public-результата (0.723): отклонение от среднего по CV укладывается в один стандартный интервал, что подтверждает отсутствие переобучения под конкретное разбиение, а не только благоприятное совпадение.

### 6.4. Подбор гиперпараметров

Objective-функция Optuna использует ту же схему кросс-валидации, а не единичное разбиение — это снижает риск подбора параметров, оптимальных для одного конкретного отрезка дат. Применен `MedianPruner`: после каждого фолда trial передает промежуточный результат (`trial.report`), и при существенном отставании от медианы предыдущих trial'ов выполнение прерывается досрочно (`trial.should_prune()`). Данный механизм позволяет провести 150 trial'ов в рамках сопоставимого бюджета времени по сравнению с 20–30 trial'ами без ранней остановки.

## 7. Модель и ансамбль

Итоговый ансамбль состоит из трех моделей градиентного бустинга — CatBoost, LightGBM и XGBoost, — с равновзвешенным усреднением предсказаний и несколькими фиксированными seed'ами на модель (бэггинг для снижения дисперсии).

Альтернативные подходы, проверенные и осознанно исключенные из финального решения:

| Подход | Результат проверки |
|---|---|
| CatBoostRanker (loss function YetiRank) как отдельная модель | ~0.52 Daily AP отдельно — существенно ниже классификационного подхода; не дает прироста в составе ансамбля |
| RandomForest / LogisticRegression в составе ансамбля | Не включены: при большом числе инженерных агрегатов ожидаемо уступают градиентному бустингу |
| Оптимизация весов усреднения вместо равных весов | Не дает прироста — равные веса близки к оптимуму, полученному перебором (0.3/0.5/0.7) |
| Четвертая модель того же семейства (дерево, Logloss) | Прирост в пределах шума CV — модели одного семейства демонстрируют высокую корреляцию предсказаний |
| Target encoding по `user_id` | Не применим — `user_id` встречается в train/test ровно один раз, признак вырождается в пропуски |

## 8. Библиотеки и воспроизводимость

**Используемые библиотеки:** CatBoost, LightGBM, XGBoost, Optuna, scikit-learn, pandas, NumPy, SciPy — все открытые, разворачиваются локально, без обращения к внешним API. Языковые модели не используются: датасет не содержит текстовых полей, для которых LLM обеспечивала бы преимущество перед табличными признаками.

**Обеспечение воспроизводимости:**

- `RANDOM_STATE = 42` зафиксирован во всех процедурах, содержащих элемент случайности;
- финальный ансамбль использует фиксированный (не генерируемый заново при каждом запуске) набор seed'ов;
- ноутбук выполняется последовательно от начала до конца на предоставленных файлах `data/train.csv`, `data/test.csv`, `data/events.csv` и формирует `submission.csv` требуемого формата без промежуточного вмешательства.
